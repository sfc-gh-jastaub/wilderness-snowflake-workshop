Overview

The situation

Wilderness bought 40% more tents for every store, but the extra buyers turned up only in New South Wales and Queensland. Those stores will run out before Christmas; every other store will have tents left over. And one batch of the Summit Tent, the tent on the catalogue cover, is coming back broken.

In Lab 1 the store managers found out where they stand. Now the merchandising team has to act, store by store: which broken tents to send back to the supplier, which tents to move between stores, and how many to reorder by 13 November. In this lab you build that plan from the raw data, plus an offer for this week's tent buyers who left without a sleeping bag.

Why not just ask CoWork?

CoWork is built for questions: one answer at a time, in a conversation. That is what a store manager needs to find out where they stand. A plan is different. It has to be complete, the same for everyone, and ready for other people to use.

  • Complete. To answer a question, CoWork reads a handful of comments. AI_CLASSIFY labels every Summit Tent return comment, so the real faults can be counted. AI_COMPLETE writes an email for each member, not just an example.
  • The same for everyone. The plan is a table that Snowflake keeps up to date, so everyone sees the same numbers every morning. A chat answer is written fresh each time and stays in one person's chat.
  • Ready to use. The merchandising team opens the plan in an app, marketing can pick up the offer list, and in Lab 3 the technical team tests and controls it all. An answer in a chat goes no further.

1

Where the tents are, and where the buyers are

~8 min

Wilderness bet on tents everywhere. Before anyone moves a tent, check the bet against the raw data, state by state: how much stock each state holds against last Christmas, and whether demand is up or down.

You use the same Cortex Code panel as this morning, in a Workspace. It turns a business question into SQL across several tables, runs it and shows you the result. You check its work by reading the numbers, not the SQL.

  1. Go to Projects » Workspaces and open the workspace with your SQL file from Lab 1.
  2. Open the Cortex Code panel and check the approvals setting at the bottom is still Bypass approvals, as in Lab 1.
  3. Paste the prompt below and send it.

Prompt 1:

cortex code
Using the WILDERNESS_HOL database and WILDERNESS_WH warehouse, can you check whether each state has enough tents for the holiday season? Compare each state's tent stock on hand as of 3 Nov 2026 with how many tents it sold from 4 Nov to 24 Dec last year. Also compare tent sales for 1–3 Nov this year with the same three days last year, so we can see whether demand is up or down. Put anything new you create in the LAB2_ANALYTICS schema.
You should see

A table by state:

  • Stock: 1.4 in every state. Each state holds 40% more tents than it sold over the same weeks last year. Wilderness really did send the extra tents everywhere.
  • Demand: two groups. New South Wales and Queensland are up 60%; every other state is up about 10%.

So New South Wales and Queensland, with 1.4 times the stock against 1.6 times the demand, run out about a week before Christmas Eve. Everywhere else, 1.4 times the stock against 1.1 times the demand, has tents left over on Boxing Day.

2

Which tents are broken

~7 min

Some Summit Tents are coming back broken. Wilderness's supplier, Kestrel, takes back faulty stock. The returns desk codes nearly every return as "faulty", so the codes cannot say which returns are real faults. The customer's comment can.

AI_CLASSIFY reads each comment and gives it one of the categories you choose. It is SQL: the model runs where the data is, on every row, and the result is a table you can join like any other.

Prompt 2:

cortex code
For each batch, how often are Summit Tents returned, and what are the most common reasons? Use the return comments and AI_CLASSIFY to group each return into one of these categories: pole fault, seam fault, couldn't pitch, changed mind, or other. Save the results as TENT_RETURN_REASONS and show the count for each reason by batch.
You should see

Batch B26-07 returned at about 18%, against about 4% for every other batch. About 450 comments labelled in a minute or so. Seven in ten B26-07 returns are a pole fault or a seam fault; the other batches' are mostly changed mind.

About one in six returns from the faulty batch are first-time campers, not faults

They are the "couldn't pitch" rows: people who could not put the tent up. The returns desk coded them "faulty" with the rest. The AI function tells them apart.

3

A sleeping-bag offer for this week's tent buyers

~7 min

Every family with a new tent needs somewhere to sleep, and some of this week's tent buyers left without a sleeping bag. The Basecamp members among them can be sent an offer.

AI_COMPLETE writes text, in SQL. You give it a prompt for each row, with that row's name, tent and store, and it returns the email in a column.

Prompt 3:

cortex code
Which Basecamp members bought a tent between 1 and 3 Nov 2026 but didn't buy a sleeping bag or mat in the same order? Save their first name, store and tent as SLEEPING_BAG_OFFER, and tell me how many there are. Then pick five of them and use AI_COMPLETE to write each one a short email, under 80 words, that thanks them for buying the tent and offers 15% off a sleeping bag or mat before Christmas. Save the emails and show them to me.
You should see

About 700 members saved in SLEEPING_BAG_OFFER, then five emails in a few seconds, each with the member's name, their tent and their store, for example "Thanks for picking up the Overland 3P Tent at our Torquay store this week". The wording changes from run to run.

Five, for review, not sent

AI_COMPLETE runs once per row and is charged by the amount of text, so check the wording on a few before anyone writes 700. The emails are saved in a table and shown on screen; nothing in this lab sends anything to a member.

4

The plan, as a dynamic table

~8 min

The faulty batch is real, so every unsold B26-07 Summit Tent goes back to Kestrel. Now put it all together, store by store: the good tents each store has, what it will sell by Christmas Eve, and whether it has tents to spare or needs more.

A dynamic table is a query whose result Snowflake keeps up to date. You write the query once; when tomorrow's sales land, the plan refreshes within the hour, with no job to schedule, and when nothing has changed the refresh is skipped.

Prompt 4:

cortex code
I want to know which stores will have too many tents this Christmas and which won't have enough.
For each store, take its tents on hand and leave out the B26-07 ones, since those are going back. Then compare what's left with how many it should sell by 24 Dec, using last year's sales from 4 Nov to 24 Dec grown by its state's growth rate. Label each store MOVE OUT if it has spare tents or MOVE IN if it's short. Save this as a dynamic table called CHRISTMAS_PLAN that refreshes every hour.
You should see

72 rows. Every store outside New South Wales and Queensland is MOVE OUT; every store in New South Wales and Queensland is MOVE IN. In total, about 5,100 tents to send back, about 2,400 spare and about 5,300 short. The spare does not cover the shortfall, so about 2,900 tents must be reordered by 13 November.

Why these numbers differ from Lab 1

This morning's assistant counted every tent on the shelf, so it saw about 5,200 tents left over and about 3,000 short. The plan takes the 5,100 broken tents off first. That leaves fewer to spare, about 2,400, and more short, about 5,300.

5

Hand it to the merchandising team

~10 min

The merchandising team will not open a Workspace. Give them the plan as an app: send back, move, reorder, and where.

Streamlit in Snowflake runs a Python app next to the data, and each person who opens it reads the data with their own rights. For a bigger build like this, Cortex Code's Plan mode first writes out what it will build and waits for you to approve it, so you can correct the plan before any code is written.

  1. In the Cortex Code panel, switch the mode from Agent to Plan.
  2. Paste the prompt below and send it.
  3. Read the plan Cortex Code proposes, then approve it to build the app.

Prompt 5:

cortex code
Before Christmas, the team needs to send back the faulty B26-07 tents, move spare stock to stores that are short, and place any reorder by 13 Nov. Can you build a simple Streamlit app called CHRISTMAS_PLANNER to help? Put it in WILDERNESS_HOL.LAB2_ANALYTICS on WILDERNESS_WH, using CHRISTMAS_PLAN joined to RAW.DIM_STORE for store locations.
Give it a festive dark green header, then four network-wide numbers:
- B26-07 tents to send back
- Tents to move (the smaller of total spare and total shortfall)
- Tents to reorder (shortfall minus spare, or zero if there's no shortfall left)
- Stores short, out of the total
Below that, add a state filter. Then put a store map next to a bar chart of the gap by state. On the map, show MOVE IN stores in red and MOVE OUT stores in green, with bubble size based on the gap. Finish with the store table, shortest stores first.
You should see

First a plan listing the parts of the app. After you approve it, a link to the app: a dark green header, then about 5,100 tents to send back, about 2,400 to move, about 2,900 to reorder and 33 of 72 stores short. Below, the map with red bubbles in New South Wales and Queensland and green everywhere else, the bar chart by state and the store table. Pick NSW and every store shows MOVE IN; pick VIC and every store shows MOVE OUT.

Switch back to Agent mode

Plan mode stays on for the next prompt. Switch back to Agent before Step 6.
